# SHA-256: from NSA's Cryptol to proved Verus

English | [日本語](sha-256.ja.md)

How the crate implements SHA-256 (FIPS 180-4) and how that implementation
is tied to NSA's Cryptol in `algorithms/SHA2/`. The counterpart of the
SPARK crate's `spark/doc/walkthroughs/sha-256.md`
(github.com/manthonyaiello/Foundation, tag `spark-v1.0`), with the same
sections, shortened: each says what the Verus code does and where it
differs, and the code itself, with its doc comments, is in the files it
names. HMAC-SHA-256 is built on top of this and has its own page,
[`hmac-sha-256.md`](hmac-sha-256.md).

There are three layers, as in the SPARK crate:

- **The spec layer** (`src/sha2/`: `notation`, `functions`,
  `preprocessing`, `main` and its instance `sha256`). `spec fn`s that
  mirror NSA's Cryptol declaration by declaration: the same names, the same
  types (words as Rust integers, bit strings as `Seq<bool>`), the same
  recursion and folds. They are never compiled.
- **The refinement layers** (`sha256_bytes`, `sha256_blocks`), also spec
  and proof code. `sha256_bytes::hash_bytes` restates the spec's bit-level
  `hash` over bytes and words, and `lemma_hash_bytes` proves the two equal.
  `sha256_blocks` holds the facts about folding the compression over runs
  of blocks that a streaming hash needs.
- **The implementation layer** (`sha256_stream`), with the executable
  twins of the spec functions (each module's `exec`). `compress`, `init`,
  `update`, `finalize`, `hash` and `hash_chunked`. Their `ensures` name the
  spec layer, and Verus proves them.

```text
               NSA Cryptol (algorithms/SHA2/*.cry)
                                                ^
                                                | SAW (compress: all inputs;
                                                |  hash: fixed lengths)
                                                | FFI (testing)
  spec layer (spec fn)                          |
                 ^                              |
                 | Verus, all inputs:           |
                 | lemma_hash_bytes             |
  sha256_bytes::hash_bytes (spec fn, bytes)     |
                 ^                              |
                 | Verus, all inputs:           |
                 | ensures, lemma_update,       |
                 | lemma_final                  |
  sha256_stream (executable) -------------------+
```

The SPARK crate's diagram also has arrows from the spec layer to the
Cryptol (the FFI check and SAW on its ghost code). Here they are missing:
a spec function is not compiled, so it is checked against the Cryptol only
through the executables that are proved equal to it ([ffi.md](../ffi.md)).

## Reading the notation

Cryptol: as in the SPARK crate's page (`[n]`, `x @ i`, `#`, `&&`, `^`,
`~`, `>>`, `>>>`, `foldl`, `/^`, `%^`, `{n, w}`, parameterized modules).

Verus:

- `spec fn` is a mathematical function, for proof only; `open` makes its
  body visible to other modules. `proof fn` is a lemma: its `requires` and
  `ensures` are its hypotheses and its conclusion.
- `fn` (an exec function) is compiled. Its `requires` and `ensures` are
  its precondition and postcondition; `old(x)` and `final(x)` are a
  `&mut` argument's value on entry and on return.
- `recommends` is a precondition that is not enforced: a spec function is
  total, and outside its `recommends` its value is unspecified by intent.
- `decreases` says why a recursion or a loop terminates.
- `invariant` states what holds at each loop iteration.
- `x@` is the view of `x`: a `Seq` for an array or a slice.
- `Seq<T>` is a mathematical sequence; `=~=` is its extensional equality,
  which is `==`.
- A trait with spec functions, implemented once per instance, is the
  counterpart of an Ada generic package and its formals.

## The spec layer, declaration by declaration

One Rust module per Cryptol module, as `src/sha2/mod.rs` says. The order
below is dependency order.

### Notation: `SHR` and `ROTR`

[`notation.rs`](../../src/sha2/notation.rs). `SHR::<n, W>` and
`ROTR::<n, W>`: Cryptol's `{n, w}` are the const generic `n` and the word
type `W` (whose width is `w`), and `n < w` is a `recommends`. `ROTR` is
stated as FIPS defines it, ``(x >> `n) || (x << `(w - n))``, as in the
SPARK crate. The executable `exec::ROTR` and `exec::SHR` on `u32` are
proved equal to them.

### Functions: `Ch` and `Maj`

[`functions.rs`](../../src/sha2/functions.rs). Generic in the word type,
as the Cryptol is polymorphic in `w`. The Cryptol takes a tuple; these take
three arguments. Their executable twins are in `functions::exec`.

### Functions: the four sigma functions

The same file: `SIGMA_256_0/1` and `sigma_256_0/1` on `u32`, each the xor
of `ROTR` and `SHR` terms, and their twins in `exec`.

### Functions and Preprocessing: the constants

`K_256` (`functions.rs`) and `H0_256`
([`preprocessing.rs`](../../src/sha2/preprocessing.rs)) are spec
functions returning `Seq<u32>`, with executable `const` arrays of the same
names in `exec`, proved equal to them.

### Main: the parameters become generic formals

[`main.rs`](../../src/sha2/main.rs). Main.cry's `parameter` block is the
trait `Parameters`, in the same order (`Word`, `d`, `w`, `Klen`, `K`, `H0`,
`SIGMA_0`, ...), and its declarations are spec functions generic over an
implementation of it, `P`. The type constraints (`fin d, d > 0`, `8 * w
>= d`, and the lengths a `Seq` does not carry) are the `ensures` of the
trait's `proof fn type_constraints`, which each implementation proves (the
SPARK crate checks them with `pragma Compile_Time_Error` at its
instance).

### Main: the instance for SHA-256

[`sha256.rs`](../../src/sha2/sha256.rs). `impl Parameters for SHA256`, as
SHA256.cry instantiates `SHA2::Main`: `Word = u32`, `d = 256`, `w = 32`,
`Klen = 64`, `K = K_256`, `H0 = H0_256` and the four sigmas.
`main::hash::<SHA256>` is SHA256.cry's `hash`. As in the SPARK crate,
there is no packaging layer (`packaging/Hash.cry`).

### Main: the message schedule `W`

`W(M, t)`: the Cryptol sequence, defined by recursion on its own
elements, is a recursive function of the index `t` (`decreases t`), and of
the block `M` that the Cryptol closes over.

### Main: one round, `step3`

`T1`, `T2` and `step3(M, vars, t)`. The Cryptol names the working
variables by a pattern `[a, b, c, d, e, f, g, h]`; here they are `vars[0]`
to `vars[7]`. The block `M` is an explicit parameter.

### Main: `step`

`step(H, M) = add(H, foldl_step3(M, H, Klen))`, where `foldl_step3` is
the prelude's enumeration fold over `[0 ..< n]` of `step3` closed over the
block: a closure, as in the Cryptol (the SPARK crate passes the block as
an explicit argument). `n` is a parameter so that the implementation's
loop invariant can name the fold after `t` rounds.

### Main: `k`, `N` and `pad`

`hash`'s local types `k` and `N` are functions of the message length
`l: nat`, through the prelude's `ceil_mod` and `ceil_div`. `pad(M) = M +
[true] + zero(k) + literal(l, 2 * w)`, with the message length below
`max_length = 2 ^^ (2 * w)`.

### Main: `parse`

`parse(p, N)` is `N` blocks, block `i` being `parse_block(p, i)`: the 16
words of the inner `split` from word `16 * i`.

### Main: `hash`

`hash(M) = join(foldl_step(H0, parse(pad(M), N), N)).take(d)`, with the
`where` locals inlined. `foldl_step` is the prelude's fold over the first
`n` blocks, recursing from the last, so that a loop's invariant after `n`
blocks is the definition.

### The rest of the spec layer

What the Cryptol has and the spec does not mirror, as in the SPARK crate:
SHA-1's `ROTL`, the SHA-224/384/512 instances, Notation.cry's and
Functions.cry's examples and properties (statements about the notation,
not functions), and `packaging/Hash.cry`.

## The Cryptol prelude in Verus

The spec is written in the prelude of `src/cryptol/`: `foldl` (twice),
`@`, `join`, `split`, `zero`, the literal of `pad`, `/^` and `%^`.
[cryptol-prelude.md](../cryptol-prelude.md) says how each is stated.

## The implementation and refinement layers

### `compress`

[`sha256_stream.rs`](../../src/sha2/sha256_stream.rs). `compress(h, m)`
ensures `final(h)@ == step::<SHA256>(old(h)@, m@)`. It computes the whole
64-word schedule (invariant: every word so far is the spec's `W`), runs the
64 rounds (invariant: the working variables are `foldl_step3` of the
first `t` rounds), and adds, as the SPARK crate's `Compress` does. Each
round is one `assert(v@ =~= step3(...))`; the step of the fold is its
definition.

### The streaming interface and `hash`

A `Context` holds the hash value, a 64-byte buffer and the byte count.
`init` models the empty message; `update(c, data)` ensures
`absorbed(old(c), data, final(c))`; `finalize` pads the buffered bytes and
compresses the last one or two blocks. `hash(M)` is `init`, one `update`
and `finalize`, and ensures both `d@ == hash_bytes(M@)` and
`bits_of(d@) == main::hash::<SHA256>(bits_of(M@))`. SPARK's `Final` is
`finalize` (`final` is reserved in Rust).

### The byte-level refinement: `hash_bytes`

[`sha256_bytes.rs`](../../src/sha2/sha256_bytes.rs). `hash_bytes(M)` is
`hash` on bytes: `pad_bytes`, `parse_bytes` and `digest_bytes` restate
`pad`, `parse` and `join` over bytes and big-endian words, and
`lemma_hash_bytes` proves `bits_of(hash_bytes(M)) == hash(bits_of(M))`
from `lemma_pad_bytes_bits`, `lemma_parse_bytes` and `lemma_digest_bytes`.
The SPARK crate's extensionality lemmas that exist because Ada's array `=`
is not the provers' equality have no counterpart; `lemma_block_ext` and
`lemma_fold_ext` (about different sequences with equal contents) are kept.

### Streaming: `models`, `lemma_update`, `lemma_final`

`models(c, M)` says that `c` is the context after exactly the bytes `M`:
its count is `M`'s length, its hash value is `step` folded from `H0` over
`M`'s whole blocks (`sha256_blocks::fold_blocks`), and its buffer holds the
bytes after them. `lemma_update` turns `absorbed` into `models(c, M +
data)`; `lemma_final` proves that `finalize`'s digest is `hash_bytes(M)`
whenever `models(c, M)`. The lemmas take the message as an argument, as in
the SPARK crate: a context does not hold it (Verus could keep it in a
ghost field; the SPARK crate's shape is kept). `hash_chunked(M, ends)`
states the result for any chunking of one slice.

## How it is checked

### Verus: every input

`cargo verus verify` proves `compress = step`, and `hash` and
`hash_chunked` equal to `hash_bytes`, which `lemma_hash_bytes` proves
equal to the spec's `hash` on the bits, for every message shorter than `Max_Bytes` (`2 ^^ 61` bytes) and
every chunking.

### The FFI check: testing against the Cryptol

[`cryptol/Verus/SHA2/`](../../cryptol/Verus/SHA2): the six functions and
the two constants against `Functions.cry` and `Preprocessing.cry`,
`load_block` against `parse`, `compress` against `step`, `hash` and the
chunked hash at the padding boundaries, at long lengths and on FIPS
180-4's vectors. The SPARK crate's properties of the spec functions
(`prop_step`, `prop_pad`, `prop_parse`, `prop_hash_bits`, ...) have no
counterpart: a spec function cannot be executed ([ffi.md](../ffi.md)).

### SAW: proof against the Cryptol at fixed sizes

[saw.md, "SHA-256 and HMAC-SHA-256"](../saw.md#sha-256-and-hmac-sha-256):
the twins of `Notation.cry` and `Functions.cry`, and `compress` against
`step` for all inputs; `hash` at twelve lengths (0, 1, 55, 56, 63, 64,
65, 100, 119, 120, 128, 200 bytes), on the LLVM bitcode and on the MIR.
The spec layer is not compiled, so SAW does not see it.

### What is proved for all inputs, and what is not

Proved for all inputs, by Verus: the executable code equals the spec
layer. Proved for all inputs, by SAW: `compress` equals NSA's `step`.
Not proved for all inputs: that the spec layer's `hash` equals NSA's
`hash`. That rests on the FFI check (testing, of the executables) and on
SAW at the twelve lengths. Unlike the SPARK crate's, the spec layer is
never compared with the Cryptol directly.

## Where spec and implementation are not one-to-one

As in [proving.md](../proving.md#where-spec-and-implementation-are-not-one-to-one):
`pad` is covered by `hash` (a streaming hash never builds the padded
message); the functions and constants of `Notation.cry`, `Functions.cry`
and `Preprocessing.cry` are spec functions with executable twins (in the
SPARK crate they are executable themselves); `hash_bytes` is the
representation layer between bytes and bits.
