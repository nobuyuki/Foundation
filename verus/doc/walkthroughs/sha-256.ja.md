# SHA-256: NSA の Cryptol から証明済みの Verus へ

[English](sha-256.md) | 日本語

crate が SHA-256（FIPS 180-4）をどう実装し、その実装を `algorithms/SHA2/` の NSA の Cryptol とどう結びつけているか。
SPARK の crate の `spark/doc/walkthroughs/sha-256.md`（github.com/manthonyaiello/Foundation、タグ `spark-v1.0`）に対応する文書で、節も同じだが短くしてある。
各節は Verus のコードが何をし、どこが違うかを述べる。コードそのものとその doc comment は、節が名指すファイルにある。
HMAC-SHA-256 はこの上に作られていて、別の文書 [`hmac-sha-256.ja.md`](hmac-sha-256.ja.md) がある。

SPARK の crate と同じく、層は 3 つある:

- **spec 層**（`src/sha2/`: `notation`、`functions`、`preprocessing`、`main` とその具体化 `sha256`）。
  NSA の Cryptol を宣言ごとに写した `spec fn` で、名前も型（ワードは Rust の整数、ビット列は `Seq<bool>`）も、再帰や fold も同じである。コンパイルはされない。
- **詳細化の層**（`sha256_bytes`、`sha256_blocks`）。これも spec と proof のコードである。
  `sha256_bytes::hash_bytes` は spec のビット単位の `hash` をバイトとワードの上で言い直したもので、`lemma_hash_bytes` が両者を等しいと証明する。
  `sha256_blocks` には、ストリーミングのハッシュが必要とする、ブロックの並びの上で圧縮関数を畳むことについての事実がある。
- **実装層**（`sha256_stream`）と、spec 関数の実行可能な双子（各モジュールの `exec`）。
  `compress`、`init`、`update`、`finalize`、`hash`、`hash_chunked`。
  その `ensures` が spec 層を名指し、Verus がそれを証明する。

```text
               NSA の Cryptol（algorithms/SHA2/*.cry）
                                                ^
                                                | SAW（compress: 全入力。
                                                |  hash: 固定の長さ）
                                                | FFI（テスト）
  spec 層（spec fn）                            |
                 ^                              |
                 | Verus、全入力:               |
                 | lemma_hash_bytes             |
  sha256_bytes::hash_bytes（spec fn、バイト）   |
                 ^                              |
                 | Verus、全入力:               |
                 | ensures、lemma_update、      |
                 | lemma_final                  |
  sha256_stream（実行可能） --------------------+
```

SPARK の crate の図には、spec 層から Cryptol への矢印（ghost コードへの FFI での突き合わせと SAW）もある。ここにはそれがない。
spec 関数はコンパイルされないので、Cryptol と比べるのは、それと等しいと証明した実行可能な関数を通してだけである（[ffi.ja.md](../ffi.ja.md)）。

## 記法の読み方

Cryptol: SPARK の crate の文書と同じ（`[n]`、`x @ i`、`#`、`&&`、`^`、`~`、`>>`、`>>>`、`foldl`、`/^`、`%^`、`{n, w}`、パラメータつきのモジュール）。

Verus:

- `spec fn` は数学的な関数で、証明のためだけのものである。`open` をつけると本体がほかのモジュールから見える。
  `proof fn` は lemma で、その `requires` と `ensures` が仮定と結論である。
- `fn`（exec 関数）はコンパイルされる。その `requires` と `ensures` が事前条件と事後条件である。`old(x)` と `final(x)` は、`&mut` の引数の入口での値と戻るときの値である。
- `recommends` は強制されない事前条件である。spec 関数は全域的で、`recommends` の外での値は意図して未規定にしてある。
- `decreases` は、再帰やループが止まる理由を述べる。
- `invariant` は、ループの各回で成り立つことを述べる。
- `x@` は `x` の view で、配列やスライスでは `Seq` である。
- `Seq<T>` は数学的な列で、`=~=` はその外延的な等しさ（`==` と同じ）である。
- spec 関数をもつ trait を具体化ごとに 1 回実装するのが、Ada の generic package とその formal に当たる。

## spec 層を宣言ごとに

`src/sha2/mod.rs` にあるとおり、Cryptol のモジュール 1 つにつき Rust のモジュール 1 つである。下の順は依存の順である。

### Notation: `SHR` と `ROTR`

[`notation.rs`](../../src/sha2/notation.rs)。`SHR::<n, W>` と `ROTR::<n, W>`。
Cryptol の `{n, w}` は const generic の `n` とワードの型 `W`（その幅が `w`）で、`n < w` は `recommends` にする。
`ROTR` は SPARK の crate と同じく、FIPS の定義どおり ``(x >> `n) || (x << `(w - n))`` と書く。
`u32` の上の実行可能な `exec::ROTR` と `exec::SHR` を、それらと等しいと証明する。

### Functions: `Ch` と `Maj`

[`functions.rs`](../../src/sha2/functions.rs)。Cryptol が `w` について多相なので、ワードの型について generic にする。
Cryptol はタプルを受け取り、こちらは 3 つの引数を受け取る。実行可能な双子は `functions::exec` にある。

### Functions: 4 つの sigma 関数

同じファイル。`u32` の上の `SIGMA_256_0/1` と `sigma_256_0/1` で、どれも `ROTR` と `SHR` の項の xor である。双子は `exec` にある。

### Functions と Preprocessing: 定数

`K_256`（`functions.rs`）と `H0_256`（[`preprocessing.rs`](../../src/sha2/preprocessing.rs)）は `Seq<u32>` を返す spec 関数で、`exec` に同名の実行可能な `const` の配列があり、それらと等しいと証明してある。

### Main: パラメータが generic formal になる

[`main.rs`](../../src/sha2/main.rs)。Main.cry の `parameter` ブロックは trait `Parameters` で、順も同じである（`Word`、`d`、`w`、`Klen`、`K`、`H0`、`SIGMA_0` など）。
その宣言は、trait の実装 `P` について generic な spec 関数になる。
型の制約（`fin d, d > 0`、`8 * w >= d`、`Seq` がもたない長さ）は trait の `proof fn type_constraints` の `ensures` で、各実装がそれを証明する（SPARK の crate は具体化のところで `pragma Compile_Time_Error` で確かめている）。

### Main: SHA-256 の具体化

[`sha256.rs`](../../src/sha2/sha256.rs)。SHA256.cry が `SHA2::Main` を具体化するのと同じく、`impl Parameters for SHA256` とする: `Word = u32`、`d = 256`、`w = 32`、`Klen = 64`、`K = K_256`、`H0 = H0_256`、それに 4 つの sigma。
`main::hash::<SHA256>` が SHA256.cry の `hash` である。
SPARK の crate と同じく、packaging の層（`packaging/Hash.cry`）はない。

### Main: メッセージスケジュール `W`

`W(M, t)`。Cryptol の列は自分自身の要素についての再帰で定義されている。ここでは添字 `t` と、Cryptol が閉じ込めているブロック `M` の再帰関数（`decreases t`）にする。

### Main: 1 ラウンド、`step3`

`T1`、`T2`、`step3(M, vars, t)`。
Cryptol は作業変数をパターン `[a, b, c, d, e, f, g, h]` で名づけるが、ここでは `vars[0]` から `vars[7]` である。ブロック `M` は明示的なパラメータにする。

### Main: `step`

`step(H, M) = add(H, foldl_step3(M, H, Klen))`。
`foldl_step3` は、ブロックを閉じ込めた `step3` の、`[0 ..< n]` の上の prelude の列挙の fold である。Cryptol と同じくクロージャにする（SPARK の crate はブロックを明示的な引数で渡す）。
`n` をパラメータにしてあるのは、実装のループ不変条件が `t` ラウンド後の fold を名指せるようにするためである。

### Main: `k`、`N`、`pad`

`hash` の局所的な型 `k` と `N` は、prelude の `ceil_mod` と `ceil_div` を通した、メッセージ長 `l: nat` の関数である。
`pad(M) = M + [true] + zero(k) + literal(l, 2 * w)` で、メッセージ長は `max_length = 2 ^^ (2 * w)` 未満である。

### Main: `parse`

`parse(p, N)` は `N` 個のブロックで、ブロック `i` は `parse_block(p, i)`、すなわちワード `16 * i` からの内側の `split` の 16 ワードである。

### Main: `hash`

`hash(M) = join(foldl_step(H0, parse(pad(M), N), N)).take(d)` で、`where` の局所定義は展開してある。
`foldl_step` は最初の `n` 個のブロックの上の prelude の fold で、最後から再帰する。そのため `n` ブロック後のループ不変条件がそのまま定義になる。

### spec 層の残り

Cryptol にあって spec が写さないもの。SPARK の crate と同じである:
SHA-1 の `ROTL`、SHA-224/384/512 の具体化、Notation.cry と Functions.cry の例と性質（記法についての言明で、関数ではない）、`packaging/Hash.cry`。

## Verus での Cryptol の prelude

spec は `src/cryptol/` の prelude で書いてある: `foldl`（2 回）、`@`、`join`、`split`、`zero`、`pad` のリテラル、`/^`、`%^`。
それぞれの書き方は [cryptol-prelude.ja.md](../cryptol-prelude.ja.md) にある。

## 実装と詳細化の層

### `compress`

[`sha256_stream.rs`](../../src/sha2/sha256_stream.rs)。`compress(h, m)` は `final(h)@ == step::<SHA256>(old(h)@, m@)` を保証する。
64 ワードのスケジュール全体を計算し（不変条件: ここまでのワードはどれも spec の `W`）、64 ラウンドを回し（不変条件: 作業変数は最初の `t` ラウンドの `foldl_step3`）、足し合わせる。SPARK の crate の `Compress` と同じである。
各ラウンドは 1 つの `assert(v@ =~= step3(...))` で、fold の 1 ステップはその定義である。

### ストリーミングのインターフェースと `hash`

`Context` はハッシュ値、64 バイトのバッファ、バイト数をもつ。
`init` は空のメッセージを表す。`update(c, data)` は `absorbed(old(c), data, final(c))` を保証する。`finalize` はバッファのバイトをパディングし、最後の 1 つか 2 つのブロックを圧縮する。
`hash(M)` は `init`、1 回の `update`、`finalize` で、`d@ == hash_bytes(M@)` と `bits_of(d@) == main::hash::<SHA256>(bits_of(M@))` の両方を保証する。
SPARK の `Final` は `finalize` である（Rust では `final` は予約語）。

### バイト単位の詳細化: `hash_bytes`

[`sha256_bytes.rs`](../../src/sha2/sha256_bytes.rs)。`hash_bytes(M)` はバイトの上の `hash` である。
`pad_bytes`、`parse_bytes`、`digest_bytes` が、`pad`、`parse`、`join` をバイトとビッグエンディアンのワードの上で言い直し、
`lemma_hash_bytes` が `lemma_pad_bytes_bits`、`lemma_parse_bytes`、`lemma_digest_bytes` から `bits_of(hash_bytes(M)) == hash(bits_of(M))` を証明する。
SPARK の crate の外延性の lemma のうち、Ada の配列の `=` が prover の等しさでないために要るものには、対応するものがない。
`lemma_block_ext` と `lemma_fold_ext`（中身の等しい別々の列について）は残してある。

### ストリーミング: `models`、`lemma_update`、`lemma_final`

`models(c, M)` は、`c` がちょうどバイト `M` を入れた後の文脈であることを述べる。
すなわち、そのバイト数は `M` の長さで、ハッシュ値は `M` のすべての完全なブロックの上で `H0` から `step` を畳んだもの（`sha256_blocks::fold_blocks`）で、バッファにはその後ろのバイトが入っている。
`lemma_update` は `absorbed` を `models(c, M + data)` に変える。`lemma_final` は、`models(c, M)` のとき `finalize` の digest が `hash_bytes(M)` であることを証明する。
lemma は SPARK の crate と同じく、メッセージを引数として受け取る。文脈はメッセージをもたない（Verus なら ghost のフィールドにもてるが、SPARK の crate の形を保った）。
`hash_chunked(M, ends)` は、1 つのスライスのどんなチャンク分けについても結果を述べる。

## 確かめ方

### Verus: すべての入力

`cargo verus verify` は `compress = step` を証明し、`hash` と `hash_chunked` が `hash_bytes` と等しいことを証明する。そして `lemma_hash_bytes` が `hash_bytes` をビットの上の spec の `hash` と等しいと証明する。
これは `Max_Bytes`（`2 ^^ 61` バイト）より短いすべてのメッセージと、すべてのチャンク分けについてである。

### FFI での突き合わせ: Cryptol に対するテスト

[`cryptol/Verus/SHA2/`](../../cryptol/Verus/SHA2): 6 つの関数と 2 つの定数を `Functions.cry` と `Preprocessing.cry` に対して、`load_block` を `parse` に対して、`compress` を `step` に対して、`hash` とチャンクに分けたハッシュをパディングの境目・長い長さ・FIPS 180-4 のベクトルで。
SPARK の crate の、spec 関数についての性質（`prop_step`、`prop_pad`、`prop_parse`、`prop_hash_bits` など）に当たるものはない。spec 関数は実行できないからである（[ffi.ja.md](../ffi.ja.md)）。

### SAW: 固定サイズでの Cryptol に対する証明

[saw.ja.md の「SHA-256 と HMAC-SHA-256」](../saw.ja.md#sha-256-と-hmac-sha-256):
`Notation.cry` と `Functions.cry` の双子、`compress` を `step` に対して全入力で、`hash` を 12 通りの長さ（0、1、55、56、63、64、65、100、119、120、128、200 バイト）で、LLVM bitcode と MIR の上で証明する。
spec 層はコンパイルされないので、SAW には見えない。

### 全入力で証明したことと、していないこと

Verus が全入力で証明したこと: 実行可能なコードが spec 層と等しいこと。
SAW が全入力で証明したこと: `compress` が NSA の `step` と等しいこと。
全入力では証明していないこと: spec 層の `hash` が NSA の `hash` と等しいこと。これは FFI での突き合わせ（実行可能な関数のテスト）と、12 通りの長さでの SAW に拠っている。
SPARK の crate と違い、spec 層を Cryptol と直接比べることはない。

## spec と実装が 1 対 1 でない箇所

[proving.ja.md](../proving.ja.md#spec-と実装が-1-対-1-でない箇所) と同じ。
`pad` は `hash` が担う（ストリーミングのハッシュはパディングしたメッセージを作らない）。
`Notation.cry`・`Functions.cry`・`Preprocessing.cry` の関数と定数は、実行可能な双子をもつ spec 関数である（SPARK の crate ではそれ自身が実行可能）。
`hash_bytes` はバイトとビットの間の表現の層である。
